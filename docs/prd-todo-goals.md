### 1.1 原始需求复述

用户原话：

> 「我希望重新设计待办，改成比如我要设立一个大的目标，然后在这个大的目标下我能不断地添加待办。」

拆解为三层含义：

1. **结构诉求**：待办要有「父—子」两级，顶层是可自由创建的**大目标**。
2. **录入诉求**：「**不断地**添加待办」——强调**连续、低摩擦**的录入体验，而不是每加一条都要走一遍全屏表单。
3. **反馈诉求**（隐含）：既然有了大目标，用户就需要看到「这个目标推进到哪了」，即**整体进度**。

## 2. 现状分析（已实读代码，非推测）

### 2.1 当前「行动系统」的真实结构

代码位置：`workbench.html` L1587-1641（数据层）、L2341-2595（渲染与交互层）、L956-1105（DOM）。

| 数组 | localStorage 键 | 同步 payload 键 | 语义 | 关键字段 |
|---|---|---|---|---|
| `notes` | `wb_notes` | `notes` | 任务（待办） | `id, title, body, prio(high/mid/low), dueDate, done, doneAt, fav, ord, created, updatedAt, deleted, deviceId, dir, cat, eta, status(todo/doing/done), focus` |
| `directions` | `wb_directions` | `directions` | 人生方向 | `id, emoji, name, cat, longGoal, quarterGoal, created, updatedAt, deleted, deviceId` |
| `reviews` | `wb_reviews` | `reviews` | 每日复盘 | `id, date, topPush, tomorrow, note, created, updatedAt, deleted, deviceId` |

**⭐ 最关键的发现：项目里其实已经存在两级结构了。**

- `directions`（人生方向）就是「大目标」的雏形；
- `notes.dir` 字段是**指向 `direction.id` 的外键**；
- `renderActDirs()`（L2390）已经在按方向聚合任务、显示「当前任务 N · 进行中 N · 待办 N」；
- `openDir()`（L2500）弹窗里已经列出了该方向下的任务列表 `#dirTasks`。

**也就是说：数据层的父子关系已经具备，缺的是「目标视角的一等公民体验」——进度、行内连续添加、目标为主的导航层级。**

### 2.2 现状为什么不满足用户

| 问题 | 具体表现 | 影响 |
|---|---|---|
| **方向不是"目标"** | `directions` 首次启动硬种 4 条（🩺医学成长/🚀创业产品/💰金融认知/🌱个人成长，L1605-1616），语义是"永远推进的长期主线"，**没有完成边界、没有进度** | 用户想要的是「设立一个大的目标」——可多个、有明确完成度 |
| **看不到进度** | `renderActDirs` 只显示「当前任务 3 · 进行中 1 · 待办 2」，**没有 x/y 完成比、没有进度条** | 用户的核心反馈缺失 |
| **添加待办摩擦极高** | 唯一入口是 FAB `#noteFab` → 打开全屏编辑屏 → 填 6 个字段（名称/备注/方向/分类/优先级/预计时间/状态/截止日）→ 点保存 → 屏幕滑回首页 | 与「**不断地**添加待办」直接冲突。加 5 条子待办要走 5 遍全屏流程 |
| **目标不是导航主干** | 首页 hub 四张卡（今日聚焦 / 人生方向 / 全部任务 / 每日复盘）平级并列，方向只是其中一张卡 | 「进目标 → 看子待办」的心智路径不存在，只能通过 `#dirModal` 弹窗侧面看到 |
| **完成动作重** | 勾完成必须进编辑屏点 `#noteDoneToggle` 再保存 | 列表里应当能一键勾 |

## 3. 产品定义

### 3.1 Product Goals

| # | 目标 | 衡量方式 |
|---|---|---|
| G1 | **让「大目标」成为待办系统的导航主干**：用户能自由创建多个大目标，进目标即看到其全部子待办 | 从首页到"某目标的子待办列表"≤ 2 次点击 |
| G2 | **把子待办录入摩擦降到接近零**：支持在目标内连续添加，不打断心流 | 连续添加 5 条子待办的操作数从当前 ~40 次交互降到 ≤ 11 次（5×(输入+回车)+1 次进入） |
| G3 | **让推进程度可见**：每个大目标随时显示「已完成 / 总数」与进度条 | 目标卡与目标详情页均可见 x/y + 百分比 |

三个目标正交：G1 管**结构**，G2 管**输入**，G3 管**反馈**。

### 3.2 User Stories

| # | 用户故事 |
|---|---|
| US1 | As a 想系统推进一件大事的用户，I want 新建一个「大目标」（如"3 个月上线工作台 APP"），so that 我有一个承载所有相关待办的容器，而不是把它们散在一张长列表里。 |
| US2 | As a 想到什么就想立刻记下来的用户，I want 在目标详情页有一个常驻输入框、敲字回车就加一条子待办、焦点不丢可以继续敲下一条，so that 我能把脑子里的十件事一口气倒出来。 |
| US3 | As a 每天执行的用户，I want 在子待办列表里直接点勾选框标记完成（不进任何编辑页），so that 完成动作和呼吸一样轻。 |
| US4 | As a 想知道自己走到哪了的用户，I want 在目标卡上看到「3/10 · 30%」和一条进度条，so that 我能判断这个目标是不是停滞了。 |
| US5 | As a 已经在用这个工作台的老用户，I want 我以前记的任务和 4 个人生方向一条都不丢、打开新版就能直接用，so that 我不用担心升级把数据搞没。 |
| US6 | As a 多端使用的用户（网页 + Windows 桌面 + 安卓），I want 目标和子待办像现有数据一样自动跨端同步，so that 我在手机上加的子待办，回到电脑上也在。 |

## 4. 数据模型与迁移方案（本 PRD 的核心决策点）

### 4.1 ⚠️ 架构硬约束（来自 `.workbuddy/memory/`，必须遵守）

1. **新增一个同步键代价很高**：同步 payload 的键在**三处**被硬编码白名单控制——
   - `supabase_store.py` L36-39 `RECORD_KEYS`
   - `server.py` L920-957 `api_push` 的 SQLite 分支（逐键 `inc.get(...)` + `merge_records`）
   - `server.py` L900 `api_pull` 的空 payload 默认值
   任一处漏改，该键的数据**在跨端同步时被静默丢弃**（不报错、不提示）。
2. **`server.py` 改动必须重启进程才生效**。2026-08-07 的 `cog_annos` / `cog_expr` 就踩过这个坑：前端已经发新键，用户没重启后端，跨端数据静默丢失。
3. `index.html` 必须与 `workbench.html` **字节级一致**（`cp workbench.html index.html`），否则会复现"改了代码用户看到旧界面"的历史大坑。

### 4.2 推荐方案：**复用 `directions` 作为 Goal，零新增同步键**（方案 A1）

**核心判断：不要新建 `cogGoals` 数组。** `directions` 已经是父级容器、`notes.dir` 已经是外键，把 `directions` 语义升级为「大目标」即可，**完全不碰后端**，规避 §4.1 的全部三个坑。

#### Goal（复用 `directions`，同步键 `directions`，localStorage `wb_directions`）

| 字段 | 类型 | 状态 | 说明 |
|---|---|---|---|
| `id` | string | 已有 | `uid()` |
| `emoji` | string | 已有 | 目标图标，默认 `🎯` |
| `name` | string | 已有 | 目标名称（必填） |
| `longGoal` | string | 已有 | 复用为「目标说明 / 为什么要做」 |
| `quarterGoal` | string | 已有 | 复用为「阶段里程碑」 |
| `cat` | string | 已有 | 医学/创业/金融/个人，**P0 保留不动**（隐藏在编辑区，避免连锁改动） |
| `created` / `updatedAt` / `deleted` / `deviceId` | — | 已有 | 同步与软删三件套，**不可动** |
| `targetDate` | `string\|null` | **新增** | 目标截止日 `YYYY-MM-DD`（P1） |
| `ord` | number | **新增** | 手动排序权重（P1） |
| `archived` | boolean | **新增** | 归档（P2） |

#### Sub-task（复用 `notes`，同步键 `notes`）

字段**完全沿用现状**，`notes.dir` 即父目标 `id`。P1 会启用已存在但未参与排序的 `ord` 字段用于目标内手动排序。

> **为什么"给已有数组的记录加新字段"是安全的？**
> `merge_records`（`server.py` L1629 前端同名实现 / `supabase_store.py`）是**按 `id` 整条记录 LWW 覆盖**，不做字段级校验、不做 schema 过滤。新字段随记录整体透传，**不需要任何后端改动**。这与"新增顶层数组键"是两回事。

#### 进度计算（纯派生，不落库）

```
subs   = notes.filter(n => !n.deleted && n.dir === goal.id)
done   = subs.filter(n => n.status === 'done').length
progress = subs.length ? done / subs.length : 0     // 显示为 "done/subs.length · NN%"
```

### 4.3 老数据迁移方案：**零写入、可逆、向后兼容**

| 场景 | 处理 | 风险 |
|---|---|---|
| 4 条默认「人生方向」（医学成长/创业产品/金融认知/个人成长） | **原样保留**，自动成为用户的前 4 个大目标，名称与 emoji 不变 | 无。用户打开即见熟悉内容 |
| `dir !== null` 的任务 | **零迁移**，已通过 `notes.dir` 挂在对应目标下 | 无 |
| `dir === null` 的散装任务 | 渲染时聚合为**虚拟目标**「📥 未归类」（`id = '__inbox__'`，**不写入 `directions` 数组、不参与同步、不落 localStorage**），用户可在其中把子待办逐条移到真实目标 | 无。纯读侧适配 |
| 用户仍在用旧版前端的另一端 | 数据结构未变（只多了几个可选字段），旧版前端读到照常工作 | 无。灰度期安全 |

**这个迁移方案不执行任何一次性数据转换脚本、不删除任何字段、不重命名任何键。**
最坏情况回滚 = 把 `workbench.html` 换回旧版本，数据完全无损。

### 4.4 备选方案：新增 `goals` 顶层键（方案 A2，**不推荐**）

若架构师认为「复用 `directions` 语义污染」不可接受，可新建 `goals` 数组。代价清单（务必全部执行）：

1. `supabase_store.py` L36-39 `RECORD_KEYS` 追加 `"goals"`；
2. `server.py` L920-957 `api_push` SQLite 分支追加 `inc_goals` + `merge_records`；
3. `server.py` L900 `api_pull` 空 payload 默认值追加 `"goals": []`；
4. `workbench.html` L4873 导出 JSON、L4927-4948 拉取合并、L4960 推送 payload 三处；
5. **必须编写并执行 `directions → goals` 的一次性迁移**（有数据丢失风险）；
6. **必须要求用户重启 `python server.py`**，否则跨端目标数据静默丢失。

**PM 结论：A2 收益（语义更干净）远小于成本（6 处改动 + 迁移风险 + 用户必须重启后端）。强烈推荐 A1。**

### 6.2 关键交互规格

| 元素 | 规格 |
|---|---|
| **行内添加输入框**（A-02，最核心） | 位于目标详情页子待办列表**顶部**、常驻。`placeholder="＋ 添加子待办，回车即可连续添加"`。回车 → 以「仅 title + dir + 默认值」创建 note（`prio:'mid'`, `status:'todo'`, `cat` 继承目标）→ 清空 value → **`input.focus()` 不释放** → 列表淡入新行。**不弹窗、不转场、不 toast 打断**（可用极轻的行淡入代替 toast） |
| **勾选框**（A-03） | `☐ / ☑`，点击即写 `status`、`done`、`doneAt`、`updatedAt` 并 `saveNotes()`；完成行文字置灰 + 删除线；进度条与头部 x/y 同步刷新 |
| **进度条** | 目标卡：细条（4px）+ 右侧 `3/10`；目标详情头部：粗条（8px）+ `3/10 · 30%`。0 子待办时进度条隐藏，显示「还没有子待办，在下面加第一条吧」 |
| **FAB 上下文化** | 屏 0 按下 = 新建目标；屏 1 按下 = 聚焦到行内输入框（等价于 A-02）；屏 2 隐藏 |
| **「📥 未归类」虚拟目标卡** | 仅当存在 `dir===null` 的未软删任务时出现；带浅色虚线边框以区别真实目标；不可编辑名称、不可删除；其详情页顶部提示「这些是没有归属目标的待办，可以逐条移动到目标里」 |
| **目标编辑** | 沿用现有 `#dirModal` 弹窗改造（新增 `targetDate` 输入），不新建弹窗组件 |

### 6.3 与「今日聚焦 / 每日复盘」的关系（明确定位，避免概念打架）

三者是**三个不同的观察轴**，互不替代：

| 模块 | 轴 | 数据源 | 本次变更 |
|---|---|---|---|
| **🎯 我的目标** | **结构轴**（这件大事由哪些小事组成） | `directions` + `notes.dir` | **本次重做的主体** |
| **🎯 今日聚焦** | **时间轴 · 当下**（今天要做哪几件，可跨目标） | `notes.focus \|\| dueDate===today`，取前 3 | **逻辑不变**，仅在子待办行增加 `☆` 快捷入口（A-13） |
| **🌙 每日复盘** | **时间轴 · 回看**（今天推进了什么） | `reviews` + 今日 `doneAt` + `times` 投入 | **逻辑不变**，仅增加「推进了 M 个目标」一行（A-14） |

一句话表述给用户：**目标决定"做什么"，今日聚焦决定"今天做哪几件"，每日复盘回答"今天推进了多少"。**
