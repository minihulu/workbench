### 1.1 原始需求复述

用户原话：

> 「github 的搜索板块，搜索逻辑好像还不太好，你也重新做吧。我是想，我想要找一个我需要的仓库，然后就能直接帮我搜索到匹配的仓库，这是可以做到的吗？**不是简单的名字搜索，而是这个仓库的实际功能符合我的需求，他就会被我搜索到。**」

核心诉求一句话：**从「关键词字面匹配」升级为「功能语义匹配」。**

## 2. 现状分析（已实读代码，非推测）

### 2.1 当前实现链路

```
用户输入自然语言                     workbench.html L2687
        ↓
buildQuery(text)                     L2600-2615  ← 问题集中区
  · STOP 停用词表（~40 词，L2598）
  · MAP 中英词典（硬编码 ~55 组，L2599）
  · 输出：anchor.map(a => a + " (" + syn.join(" OR ") + ")").join(" ")
        ↓
ghFetch(q, token)                    L2671-2685
  q + "&sort=stars&order=desc&per_page=30"   ← 硬编码
  ① 先打后端 /api/github/search
  ② 404 则浏览器直连 api.github.com
        ↓
server.py github_search()            L517-560
  · 无 GH_PROXY 且无 GH_TOKEN → 直接 502
  · urllib 请求 GitHub，透传 status + X-RateLimit-*
  · 限流 github_limiter = RateLimiter(90, 60)  每 IP 90 次/分钟
        ↓
结果卡渲染                            L2722-2732
  full_name / stars / description / language / forks / pushed_at / topics(前4)
```

### 2.2 现状为什么「搜不到功能匹配的仓库」——五个根因

| # | 根因 | 代码证据 | 后果 |
|---|---|---|---|
| **R1** | **查询完全没有 qualifier，GitHub 默认只搜 `name` + `description`** | `buildQuery` 输出的是裸关键词串，从未拼过 `in:name,description,readme` | **README 里写清楚功能的仓库根本搜不到** —— 这正是用户抱怨的「不是简单的名字搜索」的技术根源 |
| **R2** | **硬编码 `sort=stars&order=desc`，丢掉 GitHub 的 best-match 相关性排序** | L2672 `"&sort=stars&order=desc&per_page=30"` | 明星大项目霸榜，真正贴合需求的小而美仓库被埋到几百名开外 |
| **R3** | **中文需求靠 55 词硬编码词典翻译，覆盖率极低** | L2599 `MAP` 只有 ~55 组中英映射 | 词典未命中时走 L2614 `return text.trim().slice(0,40)` —— **把中文原文直接丢给 GitHub 搜索，命中率近乎为零** |
| **R4** | **生成的分组 OR 语法在 GitHub repo search 支持有限** | L2610 `anchor.map(a => a + " (" + syn.join(" OR ") + ")")` | 复杂布尔表达式可能被 GitHub 解析成字面量，反而**降低**召回 |
| **R5** | **结果卡零相关性信息** | L2722-2732 只有元数据 | 用户面对 30 条结果只能逐条点开判断，"找到"的成本没有下降 |

**结论：现状是"关键词搜索"，且是一个**有缺陷的**关键词搜索。用户的判断准确。**

### 2.3 一个必须正视的现实约束

| 检查项 | 结果 |
|---|---|
| `.env` 中是否有 LLM 密钥？ | **没有**（只有 `SUPABASE_*` / `WORKBENCH_JWT_SECRET` / `STORAGE_BACKEND`） |
| `.env.example` 中是否有 LLM 配置项？ | **没有** |
| `server.py` 中是否有任何 LLM 调用代码？ | **没有**（全文无 `deepseek` / `openai` / `llm` / `api_key` 关键字） |
| 环境里是否有可直接复用的 DeepSeek 凭据？ | 检查 `C:\Users\黄盛鸿\.workbuddy\binaries\node\workspace` 与 `~/.codex/config.toml`，**未发现 DeepSeek 配置**，仅有 `@openai/codex` 依赖 |

**⚠️ 因此 LLM 语义重排是「从零新增能力」，且必须默认关闭 + 全链路降级。这直接决定了 P0/P1 的切分：P0 必须在完全没有 LLM 的情况下就让搜索质量显著变好。**

## 3. 产品定义

### 3.1 Product Goals

| # | 目标 | 衡量方式 |
|---|---|---|
| G1 | **让用户用一句自然语言描述功能需求，就能拿到功能真正匹配的仓库** | 对 10 条典型中文需求做人工评测，Top 10 结果中"功能确实符合"的条数从现状基线提升到 ≥ 6 条 |
| G2 | **在完全没有 LLM 的环境下，检索质量仍显著优于现状** | 仅靠 P0（高级 qualifier + 多字段 + best-match）时，中文需求的非空结果率从近乎 0 提升到 ≥ 90% |
| G3 | **让"为什么这个仓库匹配你"可见**，把判断成本从"逐条点开"降到"扫一眼" | 每条语义匹配结果附一句 ≤ 40 字的匹配理由；用户判断单条结果耗时 ≤ 3 秒 |

三个目标正交：G1 管**能力上限**，G2 管**能力下限（可用性）**，G3 管**结果可解释性**。

### 3.2 User Stories

| # | 用户故事 |
|---|---|
| US1 | As a 造轮子前想先找现成方案的开发者，I want 直接输入「帮我找一个能管理每日待办的小工具」，so that 我不用先自己把需求翻译成正确的英文技术术语。 |
| US2 | As a 不确定该用什么英文关键词的中文用户，I want 系统把我的中文需求转成检索词**并展示出来**，so that 我能看懂它理解得对不对、不对时能改。 |
| US3 | As a 面对一屏结果不想逐条点开的人，I want 每条结果带一句「为什么它匹配你的需求」，so that 我能一眼筛掉"名字像但功能不对"的仓库。 |
| US4 | As a 在没配 LLM Key 的机器上使用的人，I want 搜索照样出可用结果、只是没有匹配理由，so that 功能不会因为缺一个 Key 就整体不可用。 |
| US5 | As a 被 GitHub 限流坑过的人，I want 明确知道是限流 / 网络 / Token / LLM 哪一层出了问题，so that 我能自己解决而不是干瞪眼。 |

## 4. 技术方案（分层架构，实现细节留给架构师）

> **设计原则：能力分层、逐层增强、任一层失效自动降到下一层，绝不整体失败。**

```
┌─────────────────────────────────────────────────────────────┐
│  L0  意图解析     自然语言 → {keywords[], topics[], filters} │
│      保底：本地词典增强（P0）  增强：LLM 抽取（P2）           │
├─────────────────────────────────────────────────────────────┤
│  L1  GitHub 高级检索（P0）                                    │
│      in:name,description,readme + archived:false             │
│      + best-match 排序（去掉硬编码 sort=stars）               │
│      + 多路召回合并去重                                       │
├─────────────────────────────────────────────────────────────┤
│  L2  LLM 语义重排（P1）                                       │
│      POST /api/search/rerank → 相关度 0-100 + 匹配理由        │
├─────────────────────────────────────────────────────────────┤
│  L3  降级（P0，与 L1 同期上线）                                │
│      任何 L2 异常 → 静默回落 L1 结果，标「🔎 关键词命中」      │
└─────────────────────────────────────────────────────────────┘
```

### 4.1 L0 · 意图解析层

输入：用户原话（中文/英文/混合）。输出：结构化检索意图。

```jsonc
{
  "keywords": ["todo", "task", "cli"],   // 英文检索锚点
  "topics":   ["todo-list", "productivity"],
  "language": null,                       // 用户明确说"用 Python 写的"时才填
  "minStars": null,
  "recentOnly": false
}
```

- **P0 实现（保底、零延迟、零成本）**：保留并扩充现有 `MAP` 词典 + `STOP` 停用词；补齐常见功能领域词（当前 55 组 → 建议 ≥ 200 组）；对未命中的中文做**兜底策略**——不再把中文原文直接丢给 GitHub，而是退化为"取命中的通用领域词 + 英文锚点"，并在 UI 明示「没完全理解你的需求，试试补充英文关键词」。
- **P2 实现（增强）**：由 LLM 直接抽取结构化意图，替代词典。

### 4.2 L1 · GitHub 高级检索层（P0 核心）

| 变更点 | 现状 | 目标 |
|---|---|---|
| 检索字段 | 默认仅 name + description | `in:name,description,readme`（**README 是"功能匹配"的关键载体**） |
| 排序 | 硬编码 `sort=stars&order=desc` | **默认留空 → GitHub best-match 相关度排序**；`stars` / `updated` 降级为用户可选项（P2） |
| 过滤 | 无 | `archived:false`（排除已归档死项目）；可选 `topic:<t>` / `stars:>=N` / `pushed:>YYYY-MM-DD` |
| 召回策略 | 单路 | **多路召回合并去重**：路 A `in:name,description`（精准）+ 路 B `in:readme`（功能）+ 路 C `topic:`（生态标签）；按 `full_name` 去重，**记录每条命中的路径**用于 UI 标注 |
| per_page | 30 | 30~50（供 L2 重排有足够候选） |

**后端配套改动（`server.py` L1082-1088）**：当前 `sort` 缺省会被填成 `"stars"`，需放开为「显式传空则不带 `sort` 参数」，否则前端无法拿到 best-match 排序。

**⚠️ 限流权衡**：多路召回把每次搜索的 GitHub 调用从 1 次变为 2-3 次。GitHub 匿名搜索限额仅 **10 次/分钟**。
→ **策略：未配置 Token 时自动退化为单路合一查询（`in:name,description,readme`）；配置了 Token（5000 次/小时）时才启用多路召回。**

### 4.3 L2 · LLM 语义重排层（P1，本需求的"语义"核心）

#### 新增后端接口

```
POST /api/search/rerank
Headers:  Content-Type: application/json
          X-LLM-Token: <可选，前端透传用户自填的 Key，与现有 X-GH-Token 模式对称>

Body:
{
  "query": "帮我找一个能管理每日待办的小工具",     // 用户原话，不做加工
  "candidates": [
    { "full_name":"a/b", "description":"...", "topics":["todo"],
      "language":"Go", "stars":1234, "pushed_at":"2026-07-01" }
    // ... 建议 N = 25
  ]
}

Response 200（成功）:
{ "ok": true, "fallback": false, "model": "deepseek-chat",
  "ranked": [ { "full_name":"a/b", "score": 92,
                "reason":"它是专注每日任务清单的 CLI 工具，支持标签与到期提醒" } ] }

Response 200（降级，注意仍是 200 而非 5xx）:
{ "ok": false, "fallback": true, "reason": "llm_not_configured" | "timeout" | "parse_failed" | "upstream_error" }
```

#### 关键设计约束

| 约束 | 说明 |
|---|---|
| **只传元数据，不传 README 正文** | 候选仅含 `full_name / description / topics / language / stars / pushed_at`。抓 README 会带来 N 次额外 GitHub 调用（限流）+ token 暴涨（成本与延迟） |
| **零第三方依赖** | `server.py` 是标准库零依赖工程，LLM 调用必须用 `urllib.request` 手写 OpenAI 兼容的 Chat Completions 请求 |
| **JSON 容错解析** | LLM 可能返回带 markdown 代码块的输出，服务端需截取首个 `[` 到末个 `]` 再 `json.loads`；解析失败即降级，不抛 5xx |
| **降级返回 200** | 任何失败都返回 `200 + {ok:false, fallback:true}`，让前端只需处理一条分支。**绝不能因为 LLM 挂了让整个搜索报错** |
| **独立限流** | LLM 有真实成本，不能沿用 GitHub 的 90 次/分钟。建议 `RateLimiter(10, 60)`（每 IP 10 次/分钟） |
| **默认关闭** | 未配置 Key 时 `/api/config` 返回 `llm_rerank: false`，前端**不发请求、不显示 loading、不显示错误**，静默走 L1 |

#### 新增环境变量（写入 `.env.example`）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `LLM_API_KEY` | 空 | 留空 = 功能关闭 |
| `LLM_BASE_URL` | `https://api.deepseek.com/v1` | OpenAI 兼容端点 |
| `LLM_MODEL` | `deepseek-chat` | |
| `LLM_TIMEOUT` | `10` | 服务端超时（秒） |

### 4.4 L3 · 降级策略（P0 必须与 L1 同期具备）

| 触发条件 | 行为 |
|---|---|
| `/api/config.llm_rerank === false` | 前端根本不发 rerank 请求，结果直接按 L1 展示 |
| 前端 8s `AbortController` 超时 | 保持 L1 结果不动，取消重排 loading |
| HTTP 非 200 / `ok:false` / `ranked` 为空 | 同上 |
| LLM 返回的 `full_name` 与候选对不上 | 忽略对不上的条目，其余照常重排 |

**降级时的 UI 表现**：结果卡统一标「🔎 关键词命中」，结果区顶部一行浅色提示「当前为关键词匹配结果（未启用语义重排）」，可点 × 关闭。**不弹错误、不红字告警**——对用户而言这是"正常的基础模式"，不是故障。

### 6.2 关键交互规格

| 元素 | 规格 |
|---|---|
| **两段式加载**（B-13，最影响体感） | ① 点搜索 → 骨架屏 → **L1 结果 ≤1s 出卡片**，全部标「🔎 关键词命中」；② 同时后台发 rerank，结果区顶部显示细进度条「🧠 正在理解匹配度…」；③ LLM 返回 → 卡片**原地重排（FLIP 动画或简单淡入）** + 徽章切换为「🧠 语义匹配 NN」+ 理由行淡入展开。**全程不白屏、不阻塞** |
| **匹配徽章** | 🧠 语义匹配 + 分数（分数 ≥80 绿 / 60-79 蓝 / <60 灰）；🔎 关键词命中（中性灰）。降级时全部为后者 |
| **匹配理由行** | 浅色底 + 💡 前缀，单行不折行超过 2 行；只在有 LLM 结果时出现，不占位不留白 |
| **「我理解到的需求」** | 可折叠；关键词以可删 chip 呈现，删掉后点「重新搜索」即用剩余词重搜——**让用户能纠正机器的理解**（US2 的落点） |
| **两个 Token 区块** | GitHub Token（现有，不动）+ 语义重排 Key（新增），视觉上并列、同为 `<details>` 折叠。均只存 localStorage，文案明示「不会上传任何服务器」 |
| **连接自检扩展** | 在现有四步后加第 ⑤ 步「语义重排：✅ 已配置 deepseek-chat（试调 1.2s）/ ⚪ 未配置（当前为关键词模式）/ ❌ 调用失败 xxx」 |
| **降级提示** | 结果区顶部一行浅灰提示条，非红色告警，可 × 关闭 |

## 7. 非目标（Out of Scope）

- 不做向量数据库 / 自建 embedding 索引（对单文件轻产品过重）。
- 不做全网爬取 GitHub 仓库建立本地库。
- 不让 LLM「凭空推荐仓库名」（幻觉造假仓库风险极高）——LLM 只对 GitHub 真实返回的候选做排序与解释。
- 不做代码级搜索（GitHub code search 需额外权限且限流严格）。
- 不引入任何第三方 Python 包。

## 8. 待确认问题（Open Questions）

> 以下问题需由架构师 / 主理人拍板，**不打扰用户**。每条附 PM 倾向意见。

| # | 问题 | PM 倾向 |
|---|---|---|
| Q1 | **LLM 密钥从哪来？** 现状 `.env` 无任何 LLM 凭据、`server.py` 无 LLM 代码。选项：(a) 要求用户在 `.env` 自备 Key；(b) 前端填、存 localStorage、`X-LLM-Token` 透传；(c) 项目内置公用 Key | **推荐 (b) 为主 + (a) 为辅**：与现有 `X-GH-Token` 模式完全对称，用户心智一致、部署零门槛；同时支持服务端 `LLM_API_KEY` 兜底（自托管场景）。**排除 (c)**（成本与泄露风险） |
| Q2 | 重排候选数 N 取多少？ | **N = 25**。再多 token 与延迟性价比骤降；GitHub 单页 30 条正好覆盖 |
| Q3 | 是否抓 README 摘要喂给 LLM？ | **P1 不抓**（额外 N 次 GitHub 调用会撞限流 + token 暴涨）。列为 **P2 (B-27)**，且仅对 Top 5 抓前 500 字 |
| Q4 | 多路召回把 GitHub 调用从 1 次变 2-3 次，匿名限额只有 10 次/分钟，怎么办？ | **有 Token 才多路，无 Token 单路合一**（已写入 B-04）。并在无 Token 时于 UI 提示「填 Token 可提升搜索质量」 |
| Q5 | 是否加后端缓存？ | **推荐 P1 加 5 分钟内存缓存**（`dict + TTL`，进程内即可，无需 Redis）。同 query 复用可同时省 GitHub 配额与 LLM 成本 |
| Q6 | 零结果时是否自动放宽条件重搜？ | **推荐 P1 做（B-19）**，放宽后必须明示「已放宽条件」，避免用户误以为原条件有结果 |
| Q7 | 旧的 `buildQuery` / `MAP` 词典是否保留？ | **保留并扩充**，作为 L0 的保底层（免费、零延迟、无网也能跑）。它不再是唯一路径，而是 LLM 不可用时的替补 |
| Q8 | LLM 超时阈值？ | **前端 8s（`AbortController`）/ 服务端 10s（`LLM_TIMEOUT`）**。前端更短，保证用户不会卡在 loading |
| Q9 | 重排失败时是否给用户可见反馈？ | **仅给一行可关闭的浅色提示条**，不弹错误、不红字。对用户而言这是"基础模式"，不是故障 |
| Q10 | `server.py` 改动的部署提示 | **必须在交付说明中显著提示：`server.py` 改动 + 新增 LLM 环境变量，均需用户本地重启 `python server.py` 才生效**（MEMORY 铁律，`cog_annos` 已踩过坑） |

| Q12 | 是否需要评测集？ | **建议架构师/QA 建一个 10 条中文需求的人工评测清单**（如"能管理每日待办的小工具""把网页存成 Markdown""本地跑的 AI 聊天界面"…），作为 G1/G2 的验收依据，避免"感觉变好了"这种无法验证的结论 |
